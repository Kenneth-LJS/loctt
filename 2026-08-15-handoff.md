## 3. What I built, and the decisions inside it

**Pagination** is an infinite query, not a page counter. LST-13 wants
rows appended and LST-35 wants a superseded page to never appear; both
fall out of the query key. Removing filters from that key fails both
specs — that is what pins it.

**Selection** clears on a result-set change. BLK-18 permits either that
or keeping it and stating what is off-screen; I took the first, since
the second needs every bulk action to target invisible rows. The
result-set key excludes `page`, so paging keeps the selection and
filtering drops it. Both directions are mutation-tested.

**Archive and Delete are deliberately asymmetric.** Archive is one
click; Delete needs a typed confirmation. Gating a reversible action
behind the same friction is a BLK-10 *violation* — it trains people to
type through dialogs.

**Bulk delete is gated twice**: the dialog, and
`BulkDeleteRequestSchema` requiring `confirm: "DELETE"` in the body. A
replayed POST cannot delete. Verified against a running server.

## 4. Process failures worth carrying forward

These cost real time and would cost the next reader more.

- **A console `window.fetch` patch never intercepts the app's
  requests.** I spent a long stretch convinced LST-49 was broken because
  no error rendered; the network log showed both requests returning 200.
  Playwright's `page.route` intercepts at the right layer. A console
  probe is not evidence about code holding its own fetch reference.
- **A mutation that does not compile is not a mutation.** Two "survived"
  readings were `tsc` failing on an unused variable while
  `npm run build >/dev/null 2>&1` hid it, so the suite ran against a
  stale `dist/`. Always check the build output.
- **`git checkout` does not restore an untracked file, and a `.bak`
  taken before later edits is not a restore point.** I wiped the entire
  bulk wiring from `ListView.tsx` this way and only caught it by
  grepping for the new symbols. Re-take backups after every real edit.
- **Row-count assertions pass against the wrong layer.** Twice: the
  filter-dedup case (server de-duplicates anyway) and the
  select-all-after-paging case (page 1's ids are a subset). Assert the
  thing the case actually names.
- **Some behaviour is genuinely untestable through the UI.** `selectAll`
  replacing vs unioning, and `total` from the newest vs first page. Both
  now say so in a comment rather than implying coverage.
