### `npm run test:ui` does not pass — and it is not the code

**Two full runs, both non-zero exit.** Run 1: 7 failed / 180 passed. Run 2:
1 failed / 186 passed. The failing set is not stable, which is itself the
finding.

Run 1 failures — all 30-second **timeouts**, all in specs that seed 60+
tasks through one `loctt create` subprocess each:

```
LST-13 (count is honest)      LST-13 (filter recomputes total)
LST-17 (page 2 from URL)      LST-49 (failed Load more)
LST-35 (filter mid-load)      LST-30 (malformed pagination)
BLK-24 (select-all at 5,000 tasks)
```

Run 2: only BLK-24.

**Proved flaky rather than assumed flaky.** All six re-run serially at
`--workers=1`: **6 passed in 2.0m**, individually 15.1s–23.0s against a
30-second budget. LST-13 alone takes 20.1s. Under five parallel workers
each spawning ~60 subprocesses, they cross the budget.

The failure messages are actively misleading. Under load the seed helper
reports `ENOENT: .loctt/config/projects.yaml` and `No .schema-version file
found` — which read as tracker corruption and are in fact the fixture's
own directory being torn down by its `finally` block when the enclosing
test times out mid-seed.

**This contradicts the head commit.** `c7b56c7` is titled *"the UI suite's
self-contention is fixed, not half-fixed"*. It is not fixed: batching the
field writes removed one process per field but left one `loctt create` per
task, and that is what still exceeds the budget. The handover reported
this suite green at 187; I measured 180 and 186 over two runs, both
exiting 1.

This is a **harness defect, not a product defect** — no product assertion
failed in either run. But `npm run test:ui` is a required gate command and
it does not pass, so it cannot be recorded as green.

## Findings

### F1 · blocker · One failed `/api/info` destroys the entire application

**Contradicts SHL-41 (bullets 1, 3, 4) and ERR-1 (bullets 1, 2).** Also
defeats SHL-42's whole premise that the shell survives a failure below it.

**Repro A — the plainest journey in the milestone, 100% reproducible:**

1. `loctt ui` on a seeded tracker; open `/list`; let it load.
2. Kill the server.
3. **Real-click "List" in the sidebar.**

Result, measured:

```
url:      /list
shellUp:  false          ← sidebar, header, nav all gone
rows:     0
roles:    []             ← no [role=alert] anywhere
fatal:    true           ← "Something went wrong / Failed to fetch / Retry"
```

**Repro B — no user interaction at all.** With the tab open on `/list`
and the server killed, wait. At the ~60s `refetchInterval` tick,
`/api/info` refetches, fails, and the same collapse happens
unprompted. Timed: `+15s` fine, `+35s` fine, `+55s` fine, **`+70s`
fatal**.

**Why.** `AppBootstrap.tsx:65-72` renders `<FatalError>` whenever
`info.isError`. `useInfo` carries the app-wide `refetchInterval`, so
`/api/info` is re-fetched every 60 seconds for the lifetime of the tab;
any single failure trips that branch and replaces `<AppShell>` entirely.

**Why it matters more than it looks.** This same file already contains
*two* fixes for exactly this mistake — the schema-mismatch branch
(comment at lines 32-35: *"this used to render a full-page error and the
banner was unreachable in exactly the situation it describes"*) and
SHL-40 (lines 76-80: *"this used to blank the app"*). The unreachable
server is the third instance and is unguarded.

**What the cases require, verbatim:**
- SHL-41: *"Views do not render as empty in the meantime — an
  unreachable server must never look like a tracker with no data."* The
  fatal page shows no data and no explanation of why.
- SHL-41: the state must be *"a persistent, visible state (banner or
  blocking overlay) saying the LocTT server is not responding."* It says
  *"Failed to fetch"*.
- ERR-1: *"The message says the LocTT server is not responding and that
  it may have been stopped in the terminal where `loctt ui` was run."*
  The app has this exact copy — `ServerUnreachableBanner` and the
  list-level `ErrorState` both produce it — and the fatal page uses
  neither.
- ERR-1: *"does not blame the user's network."* *"Failed to fetch"* is a
  network phrase.

**Accessibility aggravator:** `roles: []`. `FatalError` renders no
`role="alert"`, so a screen reader is told nothing at the moment the
entire app disappears. Every other error surface in this build gets this
right.

**The fix is narrow** and the pattern is already in the file: treat an
unreachable server the way schema mismatch and unknown identity are
treated — keep `<AppShell>` up (it already renders
`<ServerUnreachableBanner/>` at line 52) and let the route below show its
own error, instead of returning `<FatalError>` from the boot gate.

### F2 · major · A query in error stops polling; recovery takes up to 60s, not 5s

**Contradicts ERR-2 bullet 1** in spirit (recovery is not on the
interval it is configured for) and is the reason F1's fatal page can sit
for a minute after the server is back.

`queryClient.ts` configures `refetchInterval: query => query.state.status
=== "error" ? 5_000 : STALENESS_WINDOW_MS` with
`refetchIntervalInBackground: true` — a 5-second recovery poll. Measured
on the live observer, that resolves correctly:

```
refetchInterval resolves to 5000   refetchIntervalInBackground: true
```

But the network says it never runs. `/api/info` after the server is
killed:

```
… → 200, 200, 200
FAILED, FAILED, FAILED, FAILED, FAILED, FAILED     ← the retry burst
(nothing for ~60 seconds)
→ 200                                              ← the 60s tick, not a 5s poll
```

Directly observed: the errored `["info"]` query sat at `fetchStatus:
"idle"` with **zero** requests for a 90-second stretch while the server
was up and healthy, then recovered on the next 60s tick. A second
measurement confirmed 0 requests in a clean 10-second window.

The mechanism is in `queryObserver.js`: `#updateTimers()` is called from
`onQueryUpdate()`, and `#updateRefetchInterval` is only armed with what
`#computeRefetchInterval()` returned *at that moment*. The transition
into the error state does not re-arm the interval at the error value, so
the 5-second branch is configured and never scheduled — the same shape
of bug as round 4's: correct config, dead mechanism.

**Consequence:** ERR-2's *"retry-on-interval brings the data back"* is
satisfied only by the 60-second staleness interval. A user watching the
fatal page from F1 waits up to a minute with no sign anything is
happening. Worth noting the two findings compound: F1 makes the wrong
screen, F2 makes it persist.

`ServerUnreachableBanner`'s doc comment asserts *"The query defaults poll
an errored query, so when the server returns a query succeeds and this
clears itself."* That premise is measurably false.

### F3 · blocker · A schema-mismatched tracker hangs on "Loading…" forever

**Contradicts SHL-13, XS-34 and XS-35**, which all require the shell and
navigation to stay up with the banner visible.

**Repro, 100% reproducible on a cold load:**

1. `loctt init` a tracker, then `echo "9" > .loctt/.schema-version`.
2. `loctt ui --port <p>`; open `/list`.

The server behaves correctly — every `/api/` route 409s with a
`schema_mismatch` envelope carrying `schema_status: {kind: "future", …}`
and the full explanatory message. The client never gets there:

```
t=+142s   body: "Loading…"     alerts: 0
["info"]          status "pending"   fetchStatus "fetching"   fail 1
["user","current"] status "error"    fetchStatus "idle"       fail 2
```

`["info"]` is stuck **`pending` / `fetching`** — a phantom in-flight
fetch, with no corresponding network activity — indefinitely. Since
`AppBootstrap` gates on `info.isLoading || currentUser.isLoading`, the
spinner never clears, and `schemaStatusFromError(info.error)` is never
consulted because `info.error` is still null.

So the schema banner, which `AppBootstrap.tsx:30-38` was specifically
rewritten to make reachable, is **unreachable again by a different
route**. A reload does not help.

Note the contrast that localises it: the **interrupted-migration** branch
works perfectly (see XS-37 below), because it is checked *before* the
error gate and its own query settles. It is specifically the `future` /
`behind` / `unknown` kinds that hang.

Likely contributing: `retry: 1` is applied uniformly, so a 409 that can
never succeed is retried like a transient blip. A permanent status code
should not be retried.

### F4 · major · A malformed config file is reported as "Could not load", and as "no options"

**Contradicts SHL-43** on two of its three bullets.

Repro: write invalid YAML into `.loctt/config/labels.yaml`, reload
`/list`.

The **server half is right**, and generously so:

```json
"detail": "labels.yaml: malformed YAML: Flow sequence in block collection
           must be sufficiently indented and end with a ] at line 3, column 5"
```

The **client discards all of it**. Observed:

- The sidebar alert reads, in full: **"Could not load. Retry"**.
- `/labels\.yaml/.test(document.body.innerText)` → **false**. The file is
  never named anywhere in the UI.
- The **Label filter dropdown says "No options"** — presenting a broken
  config as an empty one, which is the same conflation ERR-1 forbids for
  the server.

SHL-43 requires: *"The error names the specific file
(`.loctt/config/labels.yaml`), states it could not be parsed, and
includes the parse error's location if the server provides one"* and
*"offers the next action (fix the YAML, or run `loctt doctor`)"*. None of
the three is present.

Its third bullet **passes**: the task list keeps working.

The fix is client-side only — the `detail` field is already on the wire,
and `ErrorState` already knows how to render a detail (as ERR-6 proves
elsewhere in this build).

## Behaviour no case covers

Proposed cases only. **Nothing here has been written into
`docs/dev/ui-test-cases/` or `docs/dev/surface-test-cases/`** — those are
the specification and are read-only to this gate.

- **PC-14 · No case says what the app owes when a *boot* read fails, as
  opposed to a *view* read.** F1 lives in this silence. SHL-41 and ERR-1
  are both written from the view's point of view; neither says whether
  `/api/info` failing may take the shell down. Given `AppBootstrap` has
  now been patched twice for adjacent cases, the general rule is what is
  missing: *the shell renders whenever the SPA has loaded, and every
  boot-read failure degrades inside it.*

- **PC-15 · No case constrains how quickly recovery must happen.** ERR-2
  says "recovers on its own" and says nothing about latency, so F2's
  60-second gap does not strictly contradict it. A case should state a
  bound, and should require the recovery attempt to be *visible* while
  it is pending.

- **PC-16 · Toggling a filter while page 2 is loaded shows the previous
  result set under the new URL, for ~3 seconds.** Repro: `/list?archived=true`
  → Load more (73 rows) → untick Show archived. The URL becomes `/list?page=2`
  and the footer reads **"Showing 1–73 of 73"** — including the 3 archived
  tasks — before self-correcting to 70/70 within 3 seconds. LST-50 is
  scoped to a *server error* and LST-35 to a *superseded response*, so
  neither covers a transient during a successful refetch. This is the same
  invariant round 4's PC-2 asked for, from a new direction: *the rows on
  screen always correspond to the query the footer is counting.*

- **PC-13 · The page scrolls horizontally below the sidebar breakpoint.**
  Carried from round 4 and now measured (F5). What the layout owes below
  900px is undecided.

- **PC-5 · Export field representation is unspecified.** Ids vs. display
  names (F7) needs a stated intent. Note the injection half of round 4's
  PC-5 has been settled in code without a case — worth writing down now
  that behaviour exists to describe.

- **PC-6 · Unknown query params are silently ignored.** `?bogus=1`
  returns the full unfiltered set (200). Defensible, but undecided, and
  it sits oddly beside F6 where an unknown `sort` is accepted while an
  unknown `dir`, `status` and `limit` are all rejected.

- **PC-1 · Key sort is lexicographic, not natural.** Carried; the CLI
  agrees, so this is consistent core behaviour predating M1.

- **PC-17 · No case says whether a permanently-failing status code may be
  retried.** `retry: 1` applies to a 409 schema mismatch, which can never
  succeed. This is a contributing factor in F3 and a reasonable thing to
  state once.

- **Positive findings worth locking in with cases.** Verified correct this
  round and currently unprotected: the delete confirmation's typed-count
  gate and its correctly hit-testing backdrop; the move toast naming old
  **and** new keys for every task, with old keys still resolving on both
  CLI and API; the broken-`task.md` notice naming the path and the likely
  cause; the interrupted-migration screen; the write-failure message
  (*"Nothing was updated"*) with disk confirmed untouched; `?limit=99999`
  clamped **and the URL rewritten to match**; priority sorting by
  configured rank rather than alphabetically; and the two distinct empty
  states.

## Assessment

M1.4's own surface is the best-behaved part of this build and was so in
round 4 as well: bulk selection, pagination, export, move, archive undo,
delete confirmation and the write-failure path all do what they claim,
with honest counts, correct persistence, and a key index that survived
two rekeys. The verification pass that took coverage 111 → 309 clearly
worked — every one of round 4's seven findings is either fixed or
demonstrably scoped, and the hardest one, the focus-manager pause, was
