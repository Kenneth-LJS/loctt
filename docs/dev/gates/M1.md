# 🚦 Milestone 1 gate

Verdict: **FAIL**
Date: 2026-08-25 (round 4)
Tree: `72b1a5d` (+ `6959712` docs), rebuilt clean; bundle `index-B9UIDhck.js`

Round 3's diagnosis is **correct about the mechanism and wrong about the
cure**. Queries really do pause; `status` stays `"pending"`,
`fetchStatus` becomes `"paused"`, the error is never recorded, and every
branch keyed on `isError` is unreachable. I reproduced that state
directly out of the live query cache. But the pause is gated on
**`focusManager.isFocused()`**, not on `onlineManager`, and
`networkMode: "always"` does not touch that gate. I confirmed
`networkMode: "always"` is present on the paused query's own options
while it was paused.

Two of round 3's three D1 reproductions are genuinely fixed, and ERR-2's
recovery is real and works. But the commit introduced **one new defect
that violates LST-49 verbatim** (a failed *Load more* now destroys the 50
rows already on screen — round 3's version at least kept them), and the
ERR-2 poll introduced **a second one**: the error panel is torn down and
replaced by loading skeletons every ~5 seconds, which makes "Show
details" impossible to open and ERR-6's detail unreachable on a 500.

Net for the milestone: **ERR-1 passes on a visible tab, ERR-2 passes,
ERR-6 passes for 400s and fails for 500s, LST-49 fails, LST-50 fails on a
backgrounded tab.**

## Does the paused-query diagnosis hold up?

**The mechanism: yes, exactly, and it is the deepest correct finding of
the four rounds.** With the server killed and a filter changed, I read
this straight out of the live query cache:

```
[["tasks-feed",{"status":["done"]}]]                      status success  fetchStatus idle
[["tasks-feed",{"priority":["critical"],"status":["done"]}]]
                                       status pending  fetchStatus paused
                                       fetchFailureCount 1
                                       fetchFailureReason TypeError: Failed to fetch
```

`status: "pending"` with a recorded failure and no error is precisely the
state round 3 could not name, and it explains why `isFetchNextPageError`
stayed false — impossible when settled, automatic when paused. That half
of the commit message is right and was worth finding.

**The cause: no.** The commit attributes the pause to
`onlineManager.isOnline()` returning false. In my browser
**`navigator.onLine` was `true` at every measurement**, including at the
instant the query was paused. The pause came from the other conjunct on
the same line of `@tanstack/query-core@5.100.14` `retryer.js`:

```js
// line 42
const canContinue = () =>
  focusManager.isFocused()
  && (config.networkMode === "always" || onlineManager.isOnline())
  && config.canRun();
```

`networkMode: "always"` satisfies the second conjunct and cannot satisfy
the first. And `focusManager.isFocused()` is:

```js
// focusManager.js
isFocused() {
  if (typeof this.#focused === "boolean") return this.#focused;
  return globalThis.document?.visibilityState !== "hidden";
}
```

So the retryer pauses whenever the **document is hidden** — a
backgrounded tab — regardless of network mode. Line 97 (`return
canContinue() ? void 0 : pause()`) is the pause site.

**The controlled comparison.** Same tree, same fixture, same server, same
real clicks, same repro; only `visibilityState` differs:

| | hidden pane | visible browser |
|---|---|---|
| Rows under the new chips | **18 stale rows** | error state, 0 stale rows |
| Footer | **"Showing 1–18 of 18"** (fabricated) | absent |
| `[role=alert]` | 0 | 1 |
| Retry control | none | present |
| Query state | `pending` / `paused` | `error` / `idle` |
| Recovery after restart | **none after 90 s** | ~5 s, automatic |

**What this means for the three previous rounds.** Rounds 1–3 all ran in
the hidden pane, so they were all seeing the focus pause. That also
retires **D3**: I could not reproduce it at all in a visible browser
(below), and round 3's note that "a listener I added myself did fire"
fits a document that is hidden — the event arrives, the paused React
tree does not re-render from it.

**What it does not mean.** This is not purely a harness artifact. A
hidden document is exactly what a user has when they switch tabs, and
LST-50 and ERR-2 both fail in that state today. The fix is smaller than
the current one, not larger: the focus gate is what needs neutralising.

## Findings

### D1 · blocker · The read failure is fixed on a focused tab and unfixed on a backgrounded one

Contradicts **LST-50** and **ERR-2** (and **ERR-1** on the stale-row
path). Three sub-findings, graded separately because two are fixed.

**1 · Stale rows under a new filter's chips — NOT FIXED on a hidden tab.**
Round 3's literal steps: load `/list?status=done` (18 Done rows), kill
the server, real-click Priority → Critical.

- URL becomes `?status=done&priority=critical`; both chips render as
  applied.
- **18 rows remain, all Medium/High** — none of them Critical.
- Footer asserts **"Showing 1–18 of 18"** for a query that never ran.
  The true answer is `total: 0`, confirmed against the restarted API.
- `[role=alert]` count 0, no Retry, no "Loading tasks".
- Query state: `pending` / `paused`, one recorded `TypeError: Failed to
  fetch`, `networkMode: "always"` present on the query.

LST-50: *"The chips do not show a filter as applied while the table still
shows the unfiltered rows underneath."* Verbatim. The same steps in a
visible browser produce the correct error state, so this is now scoped to
a hidden document rather than universal.

**2 · The empty state on a cold navigation — FIXED. Confirmed.** Load
`/board`, kill the server, real-click **List**. Renders:

> Loading tasks · The LocTT server is not responding. It may have been
> stopped in the terminal where you ran `loctt ui`. · **Retry**

One `[role=alert]`, no empty state. This satisfies ERR-1 in full,
including "names the actual likely cause" and "a retry control … is a
button". It is the best error copy in the app.

**3 · A failed *Load more* — FIXED, then broken a different way. NEW
REGRESSION.** With 50 rows loaded, kill the server, real-click **Load
more**. Round 3 saw the rows survive with no error. Now:

- **All 50 rows are destroyed** and replaced by the error alert.
- The footer beneath still reads **"Showing 1–50 of 70"** with a **Load
  more** button, under a table that shows no rows.

LST-49, fourth bullet: *"Already-loaded rows are not discarded."*
Violated exactly. This is a regression the commit introduced, and the
code comment at `ListView.tsx:377-381` says the guard exists precisely to
prevent it.

**Why the guard fails.** `loadMoreFailed = tasks.isFetchNextPageError`
(`ListView.tsx:187`). Read live at the moment the table was blanked:

```
isError: true    isFetchNextPageError: false    isFetchingNextPage: false
hasNextPage: true    state.fetchMeta: null
```

`infiniteQueryObserver.js:41-42` derives it as
`isError && state.fetchMeta?.fetchMore?.direction === "forward"`, and
`fetchMeta` is `null` once the fetch settles. So the flag is **transient
— true only while fetching**, and false in exactly the settled state the
render reads. `tasks.isError && !loadMoreFailed` is therefore true, and
the error branch replaces the table. Round 3 predicted this predicate
would not hold; it does not.

### D2 · major · The ERR-2 poll tears the error panel down every ~5 seconds

**New, introduced by this commit.** Sampling the error `tbody` every
300 ms on `/list?view=01BOGUSBOGUSBOGUSBOGUSBOGU`:

```
t=0.0s   1 row,  error text (83 chars)
t=1.8s   8 rows, skeleton, no text     ← panel destroyed
t=2.4s   8 rows, skeleton, no text
t=3.0s   1 row,  error text            ← panel rebuilt
…repeating on a ~5 s cycle
```

Consequences:

- **"Show details" cannot be opened.** `ErrorState` holds `showDetail` in
  `useState`; the remount resets it. Real clicks on it produce no change
  — the label stays "Show details", no `<pre>` appears. One click landed
  during a teardown and threw on a null element.
- **ERR-6's detail is therefore unreachable on a 500.** The server sends
  `detail: "unknown view \"01BOGUS…\""`, `ErrorState` is written to render
  it, and the user can never see it.
- The error message visibly flickers to loading skeletons on a loop.

The recovery poll itself is right and the "stop when healthy" half is
correct (0 requests in 15 s idle). What is wrong is that a refetch in the
error state re-enters `tasks.isLoading`, so the error is replaced by
skeletons on every attempt rather than being refreshed in place.

### D3 · major · Undo for archive renders below the fold — unchanged

Was D4 in round 3. Confirmed present, measured in a visible browser at
1280×800 with 50 rows loaded:

```
Undo button top : 1570px
viewport height :  800px
```

770px below the fold, and it scales with row count (round 3 measured
2396px at 64 rows). Archive is deliberately unconfirmed (BLK-10 replaced
the typed confirm with undo), so undo is the *only* safety net, and it
appears where the user cannot see it. The undo works when reached (real
click → "2 tasks restored", 68 → 70) and does not expire. The **bulk
action bar** in the same component is `position: sticky` and stays in view
at both 1280px and 800px — the correct pattern is already implemented a
few lines away.

### D4 · minor · CSV export writes raw ULIDs where the UI shows names

Unchanged (round 3's D7). `project`, `assignee`, `reporter`, `milestone`
and `sprint` all export as e.g. `01M0V2Z2F41A0PQZCPJQRBR0TJ`. Someone
opening the file in Excel gets opaque ids in every reference column. The
export is otherwise correct.

### D5 · minor · CSV formula injection is not neutralised

Unchanged (round 3's D8). A task titled `=cmd|"/c calc"!A1` exports as
`"=cmd|""/c calc""!A1"` — correct CSV, but Excel and LibreOffice still
treat a leading `=`/`+`/`-`/`@` as a formula. Low exposure for a local
tracker; free to fix with a leading apostrophe or tab.

### D6 · minor · An unknown `sort` field silently reorders rather than erroring

Unchanged (round 3's D6). `?dir=sideways` correctly 400s with *"Sort
direction must be ascending or descending."* `?sort=nonexistent_field`
returns **200** and a different ordering (`T1, T2, T3, T4, T9`). A typo'd
sort field should be rejected the way a bad direction already is.

### D7 · minor · The task-detail stub prints an uninterpolated `$key`

Unchanged (round 3's D9). `/tasks/T1` renders the literal
`Route stub: /tasks/$key`. The stub is expected (M2); printing the raw
route pattern is a bug in the stub. `/board` and `/timeline` interpolate
correctly, so this is specific to the parameterised route.

## Behaviour no case covers

Proposed cases only. **Nothing here has been written into
`docs/dev/ui-test-cases/`** — that directory is the specification and is
read-only to this gate.

- **PC-11 · No case says what the app owes a backgrounded tab.** This is
  the round's most valuable gap and it subsumes round 3's PC-10. The app
  behaves correctly when focused and wrongly when hidden, and nothing
  states which is required. Concretely: may a query pause indefinitely
  while the tab is in the background; and when the user returns to a tab
  that was hidden through an outage, what must they see? Note that any
  test using `onlineManager.setOnline(false)` — as
  `ListView.paused.test.tsx` does — is exercising the *online* conjunct
  and not the *focus* conjunct, so it cannot catch this. A test that
  reproduces it must drive `document.visibilityState` (or
  `focusManager.setFocused(false)`).

- **PC-12 · No case constrains what a refetch may do to a visible error.**
  D2 exists in that silence: ERR-2 requires recovery on an interval, and
  nothing says the error surface must survive the attempts. A case should
  require that a retry-in-progress does not destroy the error panel or the
  state the user has expanded inside it.

- **PC-2 · No case distinguishes a failed *append* from a failed
  *replace*.** Carried from rounds 2 and 3, and now demonstrated twice
  over: one predicate serves LST-49 and LST-50, and each round's fix for
  one has broken the other. A case should pin the invariant behind both:
  *the rows on screen always correspond to the query the footer is
  counting, and the chips always describe a query that ran.*

- **PC-3 · Undo placement and lifetime are unspecified.** BLK-10 removed
  the typed confirm in favour of undo, but nothing constrains where undo
  appears or how long it lives. D3 exists in that silence. A case should
  require it within the viewport at the moment of the action.

- **PC-8 · An empty tracker says "No tasks match these filters" with no
  filters applied.** Re-verified against a fresh `loctt init` with zero
  tasks on a separate port. The sentence names filters that do not exist.
  A first-run user's first screen should distinguish "you have no tasks
  yet" from "your filter matched nothing".

- **PC-13 · The page scrolls horizontally at 375px.** The table's own
  `overflow-x: auto` is correct (`clientWidth 252`, `scrollWidth 788`),
  but the *header bar* overflows — the theme toggle and "New task" button
  reach x=499 on a 375px viewport, so `document.scrollWidth` is 532. The
  900px breakpoint is an accepted judgement call; what happens below it is
  not written down anywhere.

- **PC-5 · Export field representation is unspecified.** Ids vs. display
  names (D4) and formula-injection neutralisation (D5) both need a stated
  intent.

- **PC-6 · Unknown query params are silently ignored.** `?bogus=1`
  returns the full unfiltered set (200). Defensible, but undecided —
  and it sits oddly beside D6, where an unknown `sort` is also accepted
  while an unknown `dir` is rejected.

- **PC-1 · Key sort is lexicographic, not natural.** `sort=key&dir=asc`
  places T2 after T19. The CLI agrees, so this is consistent core
  behaviour predating M1. A case should decide which it is.

- **Positive findings worth locking in with cases.** Verified correct
  this round: bulk-selection counts are honest across pages (50 → 50 with
  new rows unchecked → 70); the bulk bar is sticky and wraps cleanly at
  800px; the move toast names old **and** new keys for every task; the key
  index is semantically identical to a rebuild after two rekeys and
  `doctor` is clean; the export menu states its row count before
  committing and it matches the footer; CSV escaping is RFC-4180-correct
  with Unicode intact and archived excluded; the DSL quoting chokepoint
  defeats injection (`x" or "1"="1` → *"expected operator but got …"*,
  not a silent full result); `?limit=99999` is clamped to 200 and the URL
  rewritten to match; hostile titles are escaped in `innerHTML` with one
  `<script>` in the document; the ERR-2 poll costs nothing when healthy
  (0 requests in 15 s idle); and **the write path's failure message
  remains exemplary** — a killed server during a bulk Set produced
  *"Nothing was updated — the operation could not run. (Failed to fetch)"*
  and `loctt show T40` confirmed disk untouched.

## On the fix, and what round 5 should do differently

The commit found the right mechanism and then verified it against the
wrong conjunct. `ListView.paused.test.tsx` drives
`onlineManager.setOnline(false)`, which exercises
`onlineManager.isOnline()` — the half `networkMode: "always"` already
neutralises. It is green, it is not vacuous, and it cannot fail for the
reason the app actually breaks, because nothing in it makes the document
hidden. That is a sharper version of round 3's PC-10: the harness gap is
not "a throwaway QueryClient" but "a test that reproduces a *different*
cause than production has".

Three concrete things:

1. **The pause is `focusManager`, not `onlineManager`.** Any fix must
   neutralise `focusManager.isFocused()` in `canContinue` — the practical
   options are a `focusManager.setFocused(true)` at boot for a localhost
   app, or accepting the pause and rendering the paused state honestly
   instead of as data. Do not add more `networkMode` config; it is already
   correct and already ineffective.
2. **`isFetchNextPageError` is transient.** It is derived from
   `fetchMeta`, which is nulled when the fetch settles, so it is false in
   exactly the state the render reads. Distinguishing an append failure
   from a replace failure needs something durable — the page count at the
   time of the error, or a flag set in `onError`.
3. **Verify the next fix by reading the query cache in the browser, not
   by reading the screen.** `status` / `fetchStatus` / `fetchFailureCount`
   off the live client settle in seconds what four rounds have argued
   about from symptoms. The fiber walk used throughout this report is
   about six lines.

**On the ✅ marks.** M1.4's own surface remains the best-behaved part of
this build — bulk bar, pagination, export, move, archive undo, and the
write-failure path all did what they claim, with honest counts, correct
persistence, and a key index that survived two rekeys byte-for-byte in
meaning. Every blocker still lives in M1.2's error surface, and this round
moved that surface forward substantially: ERR-1's cold path and ERR-6's
400 path are now genuinely right, and ERR-2 exists at all for the first
time. It is closer than it has been. It is not done.
