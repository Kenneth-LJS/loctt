# 🚦 Milestone 1 gate

Verdict: **FAIL**
Date: 2026-08-25 (re-gate)

Three of the previous gate's four blockers are **genuinely fixed** — verified
independently, not taken on trust. The fourth is **not fixed, and the
non-reproduction was wrong.** A mid-session read failure still leaves rows
on screen that contradict the filter above them, and the footer states a
count for a query that never ran.

That single defect fails three M1 blocker cases outright — **ERR-1, ERR-2 and
ERR-6** — so this is not a judgement call about polish. It is the specification.

One new defect was introduced by the responsive fix: below 900px the table is
clipped by `overflow-x: hidden` with **no scrollable ancestor**, so seven of
ten columns are unreachable by any input.

---

## Suites

Not re-run, per the gate brief (68 UI specs, 419 integration, 21 e2e,
unit/typecheck/lint clean). `npm run build` was run once to make `dist/`
current before driving the browser; it completed clean.

Everything below comes from driving a real Chromium against a real seeded
tracker built for this run: `mkdtemp` → `loctt init --prefix T` → 67 tasks
(63 active, 4 archived) across 2 projects, 3 users, 1 milestone, 2 sprints,
2 labels, including hostile titles (`<script>`, `=cmd|"/c calc"!A1`, quotes +
commas + em dash, CJK, a 108-character title). Served via
`loctt ui --port 39555`.

All UI interaction used **real clicks and keystrokes** through `computer`.
`javascript_tool` was used only to *read* state (geometry, computed styles,
row contents, localStorage) and never to drive the UI. Where a finding rests
on a measurement, the raw numbers are given.

Two harness limitations, unchanged from the previous gate: `scroll` and
`left_click_drag` time out consistently. Both are noted where they bounded
what could be tested.

## Findings

### D1 · blocker · A mid-session read failure leaves rows that contradict the filter, and a footer that states a count for a query that never ran

Contradicts **ERR-1**, **ERR-2** and **ERR-6** — all three M1 blockers.

With the SPA loaded and the server killed, applying a filter shows the chip
as applied, keeps the pre-kill rows, and **states a total**. No error text,
no `[role=alert]`, no `[role=status]`.

**The cleanest reproduction, which removes any doubt about staleness:**

1. Load `/list?status=done` — 15 rows, every one `Medium` priority
2. `pkill -f "index.js ui --port 39555"`
3. Real-click **Priority → Critical**

Result: two chips, "Status: Done ✕" and "Priority: Critical ✕", above **15
rows that are all Medium**, with the footer reading **"Showing 1–15 of 15"**.
The true answer is **0** — confirmed against the API once restarted. The UI
is not merely showing stale data; it is *asserting a count* for a query it
never successfully ran.

Network confirms `net::ERR_CONNECTION_REFUSED`. Reproduced on three
independent paths: filter change, second filter change, and **sort** (URL
claims `sort=title&dir=asc`, indicator renders on Title, rows stay in
`updated_at` order).

**Root cause, and why it is subtle.** `ListView.tsx:329`:

```ts
) : tasks.isError && items.length === 0 ? (
```

Both hooks in `useTasks.ts` (lines 113 and 158) set
`placeholderData: keepPreviousData`. On a filter change the previous page is
served as placeholder while the new query key fetches; when that fetch fails,
those rows are still in `items`, so `items.length === 0` is false and the
ErrorState never renders. The guard is *deliberate* — its comment cites
LST-49, which requires a failed **Load more** to keep the 50 rows already on
screen. That requirement is correct. But the same gate silently covers the
**filter-change** case, where the retained rows are not a courtesy, they are
a lie. The two cases need distinguishing (a failed *append* keeps rows; a
failed *replace* must not), not one shared predicate.

**Why no test caught it.** `ListView.error.test.tsx` mounts fresh at `/list`,
so `items` is genuinely empty and the guard passes. The new `flow-list.spec.ts`
ERR-1 test reloads after aborting, hitting the shell boundary instead. Neither
exercises a filter change on an already-populated list. The gap is precise and
closing it is a small test, not a large one.

**ERR-2 fails too.** With the server restored for well over 30 seconds, the
UI stayed wrong — still 50 rows and "of 63" under `?priority=low`, where the
truth is 14. There is no refetch-on-reconnect and no retry interval. Recovery
happens only if the user's next action happens to build a different cache
key; the app never notices the server came back. ERR-2 requires it to
reconnect "without a manual browser reload".

**Worth saying plainly: the write path is exactly right.** The same kill,
followed by a bulk Set status, produced a red *"Nothing was updated — the
operation could not run. (Failed to fetch)"* and disk confirmed nothing
changed. One code path in this app states its failure perfectly; the other
invents an answer. The model to copy is already in the building.

### D2 · blocker · Below ~900px the table is clipped with no scrollable ancestor — seven of ten columns are unreachable

Introduced by the responsive fix in `a395023`.

The sidebar now correctly collapses to a 49px rail. But the table's wrapper
carries `overflow-hidden` (a rounded-corner styling class), and at the mobile
preset:

```
wrapper clientWidth : 282
wrapper scrollWidth : 815
wrapper overflow-x  : hidden
```

**533px of table is clipped, and no ancestor can scroll it.** Walking the
chain from `<table>` to `<html>`, every element with `scrollWidth >
clientWidth` reports `overflow-x: visible` or `hidden`; not one is `auto` or
`scroll`. Status, Priority, Type, Assignee, Labels, Due and Updated are
unreachable by any input method — not swipe, not scrollbar, not keyboard.
The user sees Key, Project, and a mid-word-clipped Title.

Even at 700px, where the rail is active, 168px stays clipped.

This is worse than the state M2 described: previously the columns were
off-screen but the layout was at least honest about overflowing. Now they are
hidden by a rule that also produces the rounded corners, so the clipping reads
as intentional design.

**Fix shape:** `overflow-x: auto` on the wrapper (keeping `overflow-y:
hidden` if the corners need it), or a dedicated scroll container inside the
rounded one. The brief's standing "wide content must scroll inside its own
container" rule applies directly.

**Reproduction:** load `/list` at 375px CSS width; read the table; observe
Status onward are absent with no way to reach them.

### D3 · major · The 900px breakpoint only applies on load, never on resize

`useSidebarCollapse` installs a `resize` listener and derives
`collapsed = stored || narrow`. In practice the listener does not take effect:

- **Load** at 700px → `aside` is **49px**. Correct.
- **Resize** from 1280px to 700px → `aside` stays **210px**. Wrong.
- **Resize** from 532px back to 1280px → sidebar stays **collapsed** until a
  reload, even with `tt-sidebar-collapsed` unset.

So the fix works for someone who arrives at a narrow window and does nothing
for someone who resizes one — which, on a desktop app, is the more common
motion. The stated intent ("a rotation or a window resize does not silently
discard a choice") is not what the code does.

**A second, latent problem in the same hook.** `toggle()` flips only `stored`,
while `collapsed = stored || narrow`. Below the breakpoint `narrow` is
permanently true, so the **Toggle sidebar button cannot expand the sidebar** —
yet it stays enabled and clickable, and each press still writes `stored`. A
user who presses it at a narrow width sees nothing happen, and then finds the
sidebar collapsed later at a wide width, having silently absorbed the click.
Either disable the control below the breakpoint with a title explaining why
(the pattern this app already uses well for the search box and New-task
button), or make it an overlay drawer.

### D4 · major · Undo for archive still renders below the fold

Unchanged from the previous gate's M1, re-measured and re-confirmed.

Archive is deliberately unconfirmed (BLK-10 replaced the typed confirm with
undo), which makes undo the *only* safety net. It is `position: static` in a
footer div at the document end:

```
Undo button top : 2470px
viewport height :  800px
```

1670px below the fold. Two rows vanish with no confirmation and nothing
appears near the user's attention. Contrast the **bulk action bar**, which is
`position: sticky` and stays in view perfectly — the correct pattern is
already implemented ten pixels away in the same component.

The undo itself works when reached (verified by real click: "2 tasks
restored", count 63, no `Archived:` on disk) and does not appear to expire.
This is placement only — but for the sole reversal of an unconfirmed
destructive action, placement is the whole feature.

### D5 · major · A 400 or 500 from the API renders as "No tasks match these filters"

Distinct from D1 (different mechanism: here `items` correctly empties) and
still open from the previous gate's B2. Contradicts **ERR-6**.

The list has no way to distinguish "the server rejected this" from "zero rows
matched". The server's message is precise and well-built and is discarded
entirely:

```
GET /api/tasks?limit=50&offset=0&status=not_a_status
→ 400 {"code":"validation_failed",
       "message":"unknown status value \"not_a_status\" at position 0",
       "field":"query","recovery":{"kind":"none"}}
```

UI: *"No tasks match these filters."*

**A 500 is worse.** `/list?view=<bogus-ulid>` returns 500 with
`detail: "unknown view …"` and renders the same sentence. ERR-6 requires the
server's reason verbatim and says it must not be flattened to "Server error"
or "Something went wrong" — rendering it as a *successful empty result* is
further from the case than either of the strings the case explicitly rejects.

**Reproduction:** navigate to `/list?status=not_a_status`, or
`/list?view=01BOGUSBOGUSBOGUSBOGUSBOGU`.

### D6 · minor · An unknown `sort` field silently reorders rather than erroring

Unchanged from M5. `?dir=sideways` correctly 400s; `?sort=nonexistent_field`
returns **200** and a third ordering, distinct from both the default and any
valid sort:

```
default              → T63, T64, T66, PLAT3, PLAT2
sort=nonexistent_…   → T1, T2, T3, T4, T5
sort=title&dir=asc   → T66, PLAT3, T65, PLAT1, PLAT2
```

A typo'd sort field should be rejected the way a bad direction already is.

### D7 · minor · CSV export writes raw ULIDs where the UI shows names

Unchanged from M3. `project`, `assignee`, `reporter`, `milestone` and
`sprint` all export as `01M0TEAP6DBQ7AW79X1T1JVDWE`. Someone opening the
export in Excel gets opaque ids in every reference column. The export is
otherwise correct.

### D8 · minor · CSV formula injection is not neutralised

Unchanged from M4. A task titled `=cmd|"/c calc"!A1` exports as
`"=cmd|""/c calc""!A1"` — correct CSV, but Excel and LibreOffice still treat
a leading `=`/`+`/`-`/`@` as a formula. Low exposure for a local tracker; free
to fix with a leading apostrophe or tab.

### D9 · minor · The task-detail stub prints an uninterpolated `$key`

Unchanged from M6. `/tasks/T36` renders the literal `Route stub: /tasks/$key`.
The stub is expected (M2); printing the raw placeholder is a bug in the stub.
`/board`, `/timeline` and the 404 stub all interpolate correctly.

## Behaviour no case covers

Proposed cases only. **Nothing here has been written into
`docs/dev/ui-test-cases/`** — that directory is the specification and is
read-only to this gate.

- **PC-1 · Key sort is lexicographic, not natural.** `sort=key&dir=asc` gives
  `PLAT1, PLAT2, PLAT3, T1, T10, T11, T12, …` — T2 lands after T19. For the
  primary user-facing identifier a user expects T1 → T2 → T10. **The CLI does
  the same**, so this is consistent core behaviour that predates M1. A case
  should decide which it is, because right now nothing says.

- **PC-2 · No case distinguishes a failed *append* from a failed *replace*.**
  This is the gap D1 lives in, and it is worth stating separately from the
  defect. LST-49 correctly requires a failed "Load more" to keep its rows.
  Nothing states the converse — that a failed *filter change* must not. One
  predicate currently serves both. A case should pin down that the rows on
  screen always correspond to the query the footer is counting.

- **PC-3 · Undo placement and lifetime are unspecified.** BLK-10 removed the
  typed confirm in favour of undo, but nothing constrains where undo appears
  or how long it lives. A case should require it within the viewport at the
  moment of the action. (Observed: it does not appear to expire, which is
  probably right, but is also unstated.)

- **PC-4 · No responsive contract exists for M1.** The 900px breakpoint is
  reasonable as a number and I would not argue with it. What is missing is
  the contract underneath: **at any width, is every column reachable?** D2
  exists because the answer was never written down. Either state "the list
  requires ≥ N px and degrades honestly below it", or require horizontal
  scroll. Silence currently reads as the clipping in D2.

- **PC-5 · Export field representation is unspecified.** Ids vs. display
  names (D7) and formula-injection neutralisation (D8) both need a stated
  intent.

- **PC-6 · Unknown query params are silently ignored.** `?bogusfilter=…`
  returns the full unfiltered set. Defensible, but undecided. Note for the
  next gate: `q=` in the URL is **not** ignored — the client translates it to
  the API's `query=` param, and the sidebar's saved filters rely on it. I
  initially recorded a defect here and withdrew it after checking the network
  panel; a case stating the mapping would save the next person the same
  detour.

- **PC-7 · `doctor`'s key-index check cannot detect a rekey.** It compares
  counts, so a key that changed identity leaves it reporting "in sync". This
  no longer has a live trigger now that B4 is fixed on the write path, but it
  remains a blind spot: the one diagnostic a user would run cannot see this
  class of corruption. A case should require the check to verify that every
  task's *current* key is present and maps to that task.

- **PC-8 · An empty tracker says "No tasks match these filters" with no
  filters applied.** Verified against a fresh `loctt init` with zero tasks:
  the sentence names filters that do not exist, and is identical to what a
  400 shows. A first-run user's first screen should distinguish "you have no
  tasks yet" from "your filter matched nothing".

- **PC-9 · An archived entity degrades to a truncated raw ULID.** Archiving
  `alice` while `?assignee=<alice>` is active leaves the Assignee column
  reading `01M0TEAP…` and the chip reading the full ULID; alice disappears
  from every dropdown. It **does** degrade visibly rather than crashing,
  which is the right shape — but "visibly" here means an opaque id where a
  name was. This is the M4 journey arriving early, so it is recorded against
  M4 rather than reported as an M1 defect.

- **Positive findings worth locking in with cases.** These were checked and
  are correct: bulk-selection counts are honest across pages (50 → 50 with
  new rows unchecked → 52); the bulk bar is sticky and stays reachable; the
  export menu states its row count before committing; CSV escaping is
  RFC-4180-correct with Unicode intact and archived excluded; the DSL
  quoting chokepoint defeats injection (`x" or "1"="1` → 0 rows); path
  traversal on `/api/tasks/../../../etc/passwd` returns the SPA shell, not a
  file; hostile titles render as text everywhere; theme persists via
  `tt-theme` with no flash and light mode is fully legible; unbuilt controls
  (search box, New task, saved-view editor) are `disabled` with a `title`
  naming the milestone they arrive in — a genuinely good pattern that D3's
  toggle button should adopt; and **the write path's failure message is the
  model the read path should copy.**

## What I could not test, and why

- **Mouse-wheel scrolling and drag.** `computer{action:"scroll"}` and
  `left_click_drag` both time out consistently in this harness. For D2 this
  does not weaken the finding — `overflow-x: hidden` with no scrollable
  ancestor means *no* input method can reveal those columns, which is a DOM
  fact rather than an interaction one. It does mean the undo in D4 was
  reached by enlarging the viewport rather than by scrolling to it.

- **Keyboard-only navigation.** Key events did not reach the document
  (`document.activeElement` stayed `BODY` after `Tab`, and `[` did not toggle
  the sidebar), so tab order and focus rings could not be verified. This is
  an M4 journey and is not owed here, but M1's shell is what it would
  exercise. D3's toggle-button claim rests on reading
  `useSidebarCollapse.ts`, where `collapsed = stored || narrow` makes the
  behaviour unambiguous, rather than on a keystroke.

- **Actual file download of the CSV.** The viewer sandboxes downloads. The
  real click was confirmed to issue the request
  (`/api/tasks/export?status=…&assignee=…&format=csv` → 200) and the
  identical URL was fetched out-of-band and parsed with Python's `csv`
  module.

- **BLK-44** (one malformed `task.md` breaks every read) excluded as already
  recorded in `known-gaps.md`. Note that **ERR-9 is an M1 blocker case
  covering exactly that behaviour**, so the known gap and the case are in
  direct conflict — worth resolving, but out of scope for this gate.

- **Task detail, board, timeline, settings, init** are stubs by design.
  Excluded per the brief. All render a stub inside the app shell rather than
  crashing or blanking, and unknown routes render "Route stub: 404" — handled
  acceptably. The one exception is D9, the uninterpolated `$key`.

## On the ✅ marks

Same shape as the previous gate found, and it is worth repeating because it
is now better evidenced. **M1.4's own surface is the best-behaved part of
this build** — bulk bar, pagination, export, move, archive undo all did what
they claim, with honest counts and correct persistence, and the move fix
stood up to three generations of rekey plus a deleted index.

Every remaining blocker lives in M1.2's error surface (D1, D5) or M1.3's
filter bar and shell (D2, D3). Those tickets are marked ✅ at 0/75, 10/67 and
3/44 cases covered, and D1 fails three named M1 blocker cases — ERR-1, ERR-2
and ERR-6 — that were never walked. The ✅ marks record "the bullets were
built"; this gate is still the first thing to walk that code against its
cases, and it is finding what that distinction predicts.

**The one thing I would change about how the last round was fixed.** Two
specs were added for the dead-server path and both pass, but neither tests
the path the journey names. A spec that kills the network and then *reloads*
tests the boot boundary; the journey says *mid-session*. When a gate finding
does not reproduce, the most likely explanation is a different reproduction
path rather than a wrong finding — and the cheapest check is to reproduce the
gate's exact steps before writing the spec that supersedes them.
