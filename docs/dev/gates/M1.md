# 🚦 Milestone 1 gate

Verdict: **FAIL**
Date: 2026-08-25

Four blockers. Three of them share one shape: **the UI asserts a filter is
applied and shows data that does not match it.** The fourth breaks P-7/P-9 —
after a move, a task's *current* key does not resolve while its retired key
does.

None of these is an edge case. B1 and B2 are reachable in two clicks from a
cold load, on the primary filter control.

---

## Suites

The mechanical half was run separately and passed: 65 UI specs, 419
integration, 21 e2e, unit / typecheck / lint all clean. **Not re-run here**,
per the gate brief. `npm run build` was run once to make `dist/` current
before driving the browser.

Everything below comes from driving a real Chromium against a real seeded
tracker (63 tasks, 2 projects, 3 users, 2 sprints, 1 milestone, 1 label,
4 archived) via `loctt ui --port 39471`. All UI interaction used real
clicks and keystrokes. `javascript_tool` was used only to *read* state
(scroll geometry, localStorage, computed styles, row counts) and never to
drive the UI.

## Findings

### B1 · blocker · Every ULID-valued filter returns 400, and the UI shows unfiltered or stale data anyway

`dslAtom` at `apps/web/src/server/server.ts:681` decides a value needs no
quoting:

```ts
if (/^[A-Za-z0-9_.-]+$/.test(value)) return value;
```

The doc comment above it claims "Bare identifiers … — which all ids and
workflow keys are — pass through unquoted". **That premise is false for
ULIDs.** A ULID encodes a timestamp, so it always begins with a digit; the
DSL tokenizer reads the leading `01` as a number and chokes on the rest.

This fails 100% of the time, not intermittently. It affects **project,
milestone, sprint, labels, assignee, reporter** — every structured filter
whose value is an id. Only enum filters (status, priority, type) work.

```
GET /api/tasks?assignee=01M0TAGDWA7XSKWF786GM71RAK
→ 400 {"code":"validation_failed",
       "message":"unexpected token \"M0TAGDWA7XSKWF786GM71RAK\" at position 13"}
```

A leading letter parses fine (`project = ABCDEF` → 200), which pins the
cause precisely. The quoted form is entirely correct — `project =
"01M0TAGE…"` returns exactly the 2 Platform tasks, a bogus id returns 0,
`assignee = "01M0TAGD…"` returns 19. **The fix is to quote unconditionally,
or to exclude leading-digit values from the bare-identifier path.**

The client already does this correctly: `apps/web/src/client/sidebar/builtinFilters.ts:72`
builds `assignee = "${currentUserId}"` with quotes, and those sidebar
filters work. Two conventions in one repo; the server's is broken.

**Reproduction (the two-click user path):**
1. Load `/list`
2. Click the **Assignee** filter → click **alice**
3. Chip reads "Assignee: alice", dropdown ticks alice — **and every visible
   row is assigned to ken.** Network shows the request → **400**.

**Two distinct renderings of the same 400, both wrong:**
- From a clean URL (`/list?project=<id>`) → **"No tasks match these filters."**
  PLAT1 and PLAT2 exist and were visible seconds earlier.
- With a prior successful response in hand → the **stale previous result set
  stays on screen** under the new filter's chip.

### B2 · blocker · A 400 from the API renders as "No tasks match these filters"

Distinct from B1's cause, and the more general defect: the list has **no
error path for a failed response at all.** It cannot distinguish "the server
rejected this" from "zero rows matched".

```
GET /api/tasks?limit=50&offset=0&status=not_a_status → 400 Bad Request
```

The server returns a precise, well-built message — `unknown status value
"not_a_status" at position 0`, with `field` and `recovery` — and the UI
discards all of it, showing an empty table. The only trace is a console
error the user will never open.

This is the failure mode `4bb211b` ("a failed fetch no longer renders as an
empty tracker", ERR-1) was meant to close. That commit fixed the
**boot-time** path; the **400-response** path is still open.

**Reproduction:** navigate to `/list?status=not_a_status`. Table reads "No
tasks match these filters." DevTools Network shows 400.

### B3 · blocker · A mid-session read failure is completely silent

With the SPA loaded, kill the server, then click any filter.

The fetch fails with `net::ERR_CONNECTION_REFUSED`. The UI shows the new
filter chip as applied and **keeps the pre-kill rows on screen** — rows that
contradict the filter. Zero error text anywhere in the DOM, zero
`[role=alert]` / `[role=status]` nodes.

This is the journey the brief names — "confirm the failure is stated, not
rendered as empty" — and for reads it is neither stated nor empty: it is
stated *incorrectly*.

**Worth saying plainly: the write path gets this exactly right.** The same
kill, followed by a bulk "Set status → Done", produces a red *"Nothing was
updated — the operation could not run. (Failed to fetch)"*, and disk
confirmed nothing changed. The read path needs the treatment the write path
already has.

**Reproduction:**
1. Load `/list`, let it settle
2. `pkill -f "index.js ui --port <port>"`
3. Click **Status → Backlog**
4. Chip says "Status: Backlog"; table still shows In progress / Won't do rows.

### B4 · blocker · After a move, the new key 404s while the retired key resolves — violates P-7 / P-9

`move` writes the new key into the task file but **never inserts it into the
key index**. The index retains only the old key.

```
# immediately after moving T-5 → PLAT5 via the UI
GET /api/tasks/PLAT5  → 404 {"code":"not_found","message":"task not found: \"PLAT5\""}
GET /api/tasks/T-5    → 200
```

The list renders `PLAT5` and links to `/tasks/PLAT5` — **a dead link the app
just created.** Proven at the file level:

```
task.md            : key: PLAT4          (and key: PLAT3)
key-index.yaml     : T-3, T-4 present; PLAT3, PLAT4 absent entirely
```

`doctor --rebuild-index` rebuilds to **65 entries where the live index held
63** — the two moved keys were the missing pair — after which both `PLAT4`
and the historical `T-3` resolve correctly.

**This is core, not web-only:** `loctt show PLAT4` fails identically. The web
Move-to-project button is simply a first-class way to reach it.

**Against the invariants:** P-7 requires the old key keep resolving — it
does. But P-9 warns of "a task whose `project` and `key` disagree —
unreachable by either"; here the task is reachable *only* by its retired key,
which is the same corruption in a milder dress. Not in `known-gaps.md`.

**Compounding: `doctor` reports this as healthy.** It printed `✓ key index:
63 entry/entries, in sync` against a broken index. The check appears to
compare counts, and a key that *changed identity* leaves the count intact —
so the one diagnostic a user would run to catch this cannot see it.

**Reproduction:** select any task in the default project → **Move to project
→ Platform** → note the new key in the table → request `/api/tasks/<newkey>`
→ 404.

### M1 · major · Undo for archive renders below the fold

Archive is deliberately unconfirmed (BLK-10 replaced the typed confirm with
undo), which makes the undo the *only* safety net. It is `position: static`
at the document end.

Archiving from the top of a 58-row list puts the Undo button at **y ≈ 2221 in
a 720px viewport** — over 1500px below the fold. From mid-list it measured
y ≈ 995. Nothing appears near the user's attention: the rows simply vanish.

Two things make it worse: `<main>` is the scroll container and does not
respond to `End` from body focus, and **clicking a row navigates to the task**
— so a user scrolling to hunt for Undo can easily lose it instead.

The undo *works* when reached (verified: T-53 restored, count 57→58, no
`Archived:` field). This is placement only — but for the sole undo of an
unconfirmed destructive action, placement is the whole feature.

### M2 · major · No responsive handling; the table is off-screen at narrow widths

At the mobile preset the layout does not adapt. Measured at a 532px layout
width:

- `aside` = **210px**, `main` = **165px** — the sidebar is given more room
  than the content
- the table needs **760px**; only "Key" and a sliver of "Project" are visible
- filter buttons stack into a tall single column
- the **Export** button floats **overlapping** the filter column
- "Show archived" wraps mid-label

A "Toggle sidebar" button exists, but the sidebar does not auto-collapse and
is not an overlay, so the default narrow-viewport state is unusable. This is
the brief's standing "one flow at a narrow viewport" requirement.

### M3 · minor · CSV export writes raw ULIDs where the UI shows names

`project`, `assignee`, `reporter`, `milestone`, and `sprint` export as
`01M0TAGE2MC356J30ZQXCHP4FK`. On screen these resolve to `bob`, `Platform`,
`v1.0`. Someone opening the export in Excel gets opaque ids in every
reference column. The export is otherwise correct and well-escaped.

### M4 · minor · CSV formula injection is not neutralised

A task titled `=cmd|"/c calc"!A1` exports as `"=cmd|""/c calc""!A1"`. Quoting
is correct CSV but does not stop Excel/LibreOffice from treating a leading
`=` / `+` / `-` / `@` as a formula. Standard mitigation is a leading
apostrophe or tab. Low exposure for a local tracker — it needs a hostile task
title — but it is free to fix.

### M5 · minor · An unknown `sort` field silently reorders rather than erroring

`?dir=sideways` correctly 400s ("Sort direction must be ascending or
descending"). `?sort=nonexistent_field` returns **200** and yields a *third*
ordering, distinct from both the default and any valid sort:

```
default              → PLAT5, PLAT4, PLAT3, T-61, T-53
sort=nonexistent_… → T-1, T-2, PLAT4, PLAT3, PLAT5
sort=title&dir=asc   → T-61, T-9, PLAT1, PLAT2, T-1
```

A typo'd sort field should be rejected the way a bad direction already is.

### M6 · minor · The task-detail stub prints an uninterpolated `$key`

`/tasks/T-11` renders the literal string `Route stub: /tasks/$key`. The stub
itself is expected (M2); printing the raw placeholder instead of the actual
key is a small bug in the stub. `/board` and `/timeline` interpolate
correctly (`Route stub: /board`).

## Behaviour no case covers

Proposed cases only. **Nothing here has been written into
`docs/dev/ui-test-cases/`** — that directory is the specification and is
read-only to this gate.

- **PC-1 · Key sort is lexicographic, not natural.** `sort=key&dir=asc`
  yields `T-13, T-17, …, T-49, T-5, T-53, T-57, T-9`. T-5 lands between T-49
  and T-53; T-9 sorts last. For the primary user-facing identifier a user
  expects T-5 → T-9 → T-13. **The CLI does the same**, so this is core
  behaviour consistent across surfaces and predates M1 — recorded as a
  proposed case, not an M1 defect. A case should decide whether key ordering
  is natural or lexicographic, because right now nothing says.

- **PC-2 · No case states what the list does with a non-200.** B1/B2/B3 are
  all the same missing contract seen from three angles. A case should pin
  down: a 400 is distinguishable from an empty result; a failed refetch does
  not leave contradicting rows under an active chip; and the filter chip
  reflects what was *applied*, not what was *requested*.

- **PC-3 · Undo placement is unspecified.** BLK-10 removed the typed confirm
  in favour of undo, but nothing constrains where the undo appears or how
  long it lives. A case should require it within the viewport at the moment
  of the action.

- **PC-4 · No responsive contract exists for M1.** Worth an explicit
  decision — either "the list requires ≥ N px" (stated, and the narrow case
  degrades honestly) or a real breakpoint. Silence currently reads as the
  broken layout in M2.

- **PC-5 · Export field representation is unspecified.** Ids vs. display
  names in CSV (M3), and formula-injection neutralisation (M4), both need a
  stated intent.

- **PC-6 · Unknown query params are silently ignored.** `?q=…` and
  `?bogusfilter=…` both return the full unfiltered set. Defensible, but
  undecided — and it cost real time here: `?q=` looks exactly like a filter
  and silently is not one. (`query=` is the real param.)

- **PC-7 · `doctor`'s key-index check cannot detect a rekey.** It compares
  counts, so a key that changed identity leaves it reporting "in sync" over a
  broken index (B4). A case should require the check to verify that every
  task's *current* key is present and maps to that task.

- **Positive findings worth keeping.** These were checked and are correct;
  cases would lock them in: bulk-selection counts are honest across pages
  ("50 selected · 50 on this page" → "52 selected"); the export menu states
  its row count before committing; CSV escaping is RFC-4180-correct with
  Unicode intact and archived rows excluded; back/forward restores checkbox
  state from the URL; theme persists via `tt-theme` in localStorage with no
  flash; hostile titles render as text everywhere; archived rows carry a
  clear ARCHIVED badge; **and the write path's failure message is a model of
  what the read path should do.**

## What I could not test, and why

- **Keyboard-only navigation.** Key events were delivered to the browser pane
  rather than the document (`document.activeElement` stayed `BODY` after
  `Tab`), so tab order and focus rings could not be verified. One observation
  is recorded as **unconfirmed**: at the narrow viewport a `Tab` appeared to
  land on "Board", skipping the sidebar toggle and the search box. This needs
  a real keyboard pass — it is a stated M4 journey, so it is not owed here,
  but M1's shell is what it would exercise.
- **Actual file download of the CSV.** The viewer sandboxes downloads. The
  click was confirmed to issue the real request
  (`/api/tasks/export?status=…&format=csv` → 200) and the identical URL was
  fetched and parsed out-of-band.
- **Mouse-wheel scrolling.** `computer{action:"scroll"}` timed out
  consistently in this harness. Scroll positions were verified by reading
  geometry instead; note that the **`<main>`-as-scroll-container** design is
  what makes M1's off-screen Undo hard to reach, so this deserves a real
  scroll pass.
- **BLK-44** (one malformed `task.md` breaks every read) was excluded as
  already recorded in `known-gaps.md`.

## On the ✅ marks

The brief predicted findings in M1.1–M1.3 rather than M1.4, and that is what
happened. M1.4's own surface — bulk bar, pagination, export, move, archive
undo — was the **best-behaved** part of this walk: honest counts, correct
persistence, a genuinely good write-failure message. Every blocker lives in
the filter bar (M1.3), the error surface of the list (M1.2), or core.

B4 is the exception to that framing: it is a core `move` defect, not a web
one, and it will misreport as healthy under `doctor` until that check is
strengthened too.
