## Findings

### D1 · blocker · A mid-session read failure is reported three different wrong ways, none of them an error

Contradicts **ERR-1**, **ERR-2**, **ERR-6** (all M1 blockers) and **LST-50**
(M1 major). No test claims any of the four.

`12d93c8` replaced `items.length === 0` with

```ts
const loadMoreFailed = tasks.isError && (tasks.data?.pages.length ?? 0) > 0;
```

This is the same condition rewritten, not a different one. `items` is
derived from the *same* object on the line above:

```ts
const items = useMemo(() => (tasks.data?.pages ?? []).flatMap(p => p.items), …)
```

With `placeholderData: keepPreviousData`, React Query returns the **previous
query's** `data` under the new key while the new key fetches. So when a
filter change fails, `tasks.data.pages` is the *old* query's pages —
non-empty — and `loadMoreFailed` is true. The rows and the guard read the
same stale object, so they can never disagree.

**Three reproductions, all on this tree, all with the server killed by
`pkill` and the browser left untouched:**

**1 · Stale rows + a fabricated count** (round 2's exact steps)

1. Load `/list?status=done` → 14 rows, every one `Done`/`Medium`
2. `pkill -f "index.js ui --port 39777"`
3. Real-click **Priority → Critical**

Result: two chips, "Status: Done ✕" and "Priority: Critical ✕", above **14
rows that are all Medium**, footer **"Showing 1–14 of 14"**. `[role=alert]`
count 0, no Retry, no "Loading tasks". The API once restarted returns
`total: 0`. The UI is not merely stale; it *asserts a count* for a query it
never ran. This is LST-50 almost verbatim: "The chips do not show a filter
as applied while the table still shows the unfiltered rows underneath."

**2 · The empty state, which ERR-1 explicitly forbids** — a regression

1. Load `/board` (never visit `/list` in this tab)
2. Kill the server
3. Real-click **List** in the sidebar

Result: **"No tasks match these filters."** No footer, no Retry, no error.
Confirmed in a brand-new tab with no `/list` cache, and re-checked after
retries settled (network shows two `ERR_CONNECTION_REFUSED`, so `retry: 1`
is exhausted and the query is in a settled error state).

ERR-1: *"It does **not** render the empty state, 'No tasks found', '0
tasks', or an empty table. A server that is down and a tracker that is empty
must be visibly different screens; conflating them reads as data loss."*
That is the exact bug `ListView.error.test.tsx`'s header says was fixed —
the new predicate reintroduced it on a path the old one covered.

**3 · A silent failed Load more** — LST-49's error half missing

Kill the server with 50 rows loaded, real-click **Load more**. Rows and
footer correctly survive (LST-49's data half passes), but the footer renders
exactly `Showing 1–50 of 66` + a button reading **"Load more"** — no error
paragraph, no "Retry" label. Network confirms the page-2 request failed.
`Pagination.tsx` is written correctly and would render both; the call site
gates on `tasks.isFetchNextPageError`, which stayed false. The user can
click forever and nothing tells them why nothing happens.

LST-49: *"An error appears near the control naming the failure and offering
retry."*

**ERR-2 fails as well.** With the server restored for minutes, the UI stayed
wrong on every path above. `queryClient.ts` sets `refetchOnWindowFocus:
false` and `retry: 1`, and there is no reconnect handler or retry interval,
so nothing ever notices the server came back. ERR-2 requires "a
retry-on-interval or refetch-on-reconnect brings the data back… without a
manual browser reload".

**Why the suites are green.** `ERR-1`, `ERR-2`, `ERR-6` and `LST-50` have
**no `@verifies` tag anywhere in `apps/web`** — of 37 tags, the ERR ones
present are 7, 11, 13, 14, 15, 16, 18, 22, 25, 31. Beyond that, every test
mounts a **fresh `QueryClient` with `gcTime: 0` and `retry: false`**, so
`tasks.data` is genuinely `undefined` and `loadMoreFailed` is false —
the opposite of production, which uses one long-lived client with
`staleTime: 30_000`. No test exercises two successive query keys against a
shared client, which is the only configuration in which this bug exists.
The `LST-49` test passes for that reason and asserts an alert the real app
does not render.

**Fix shape (not applied — this is a gate).** The predicate needs to ask
whether *this* query key has a settled successful page, which
`tasks.data.pages` cannot answer while `keepPreviousData` is in play.
`useInfiniteQuery` exposes `isPlaceholderData` for exactly this, and
`isFetchNextPageError` distinguishes an append failure from a query failure.
Whatever shape is chosen, the test that covers it must use a **shared,
long-lived QueryClient across two query keys**, or it will pass against the
bug the way the current ones do.

### D3 · major · The 900px breakpoint still applies only on load, and the disabled toggle now makes that visible

The disabled state itself is correct and is a real improvement (see the
table above). The problem is the half of round 2's D3 that was not
addressed.

`useSidebarCollapse` installs a `resize` listener and derives
`collapsed = stored || narrow`, `canToggle = !narrow`. The listener does not
take effect:

- **Load** at 800px → aside **49px**, toggle **disabled**. Correct.
- **Resize** 800px → 1280px → aside stays **49px**, toggle stays
  **disabled**, `stored` is `null`.
- **Reload** at 1280px → aside **210px**, toggle **enabled**. So it is purely
  the resize path.

Round 2 reported this as "the fix works for someone who arrives at a narrow
window and does nothing for someone who resizes one". Disabling the button
has made that worse rather than neutral: the user is now stuck at a 49px
rail on a 1280px window, **and** the only control that could fix it is
greyed out with a tooltip saying "The sidebar stays collapsed at this
width", which is false at 1280px. Before, the click was at least absorbed
silently; now the app states a wrong reason.

I could not determine why the listener fails to re-render — a listener I
added myself did fire on the same event, so `resize` is reaching the window.
That is a code question, not a gate question; the observable behaviour above
is what the finding rests on.

**A related gap, unverified.** `toggle` is called unconditionally by the `[`
keydown handler, which is not gated on `canToggle`. On the code as written
that would write `stored` at a narrow width — the exact behaviour the commit
set out to remove. I could not confirm it: key events do not reach the
document in this harness (`stored` stayed `null` after a real `[` press).
Recorded as a code observation, not a confirmed defect.

### D4 · major · Undo for archive renders below the fold — unchanged, and further away than round 2 measured

Archive is deliberately unconfirmed (BLK-10 replaced the typed confirm with
undo), which makes undo the *only* safety net. It is `position: static` in a
footer at the document end, **below all 64 rows**:

```
Undo button top : 3196px
viewport height :  800px
```

2396px below the fold — further than round 2's 1670px, because the finding
scales with row count. Two rows vanish with no confirmation and nothing
appears near the user's attention.

The undo works when reached (real click → "2 tasks restored", count back to
66) and does not appear to expire. Contrast the **bulk action bar**, which
is `position: sticky` and stays in view perfectly at both 1280px and 800px —
the correct pattern is already implemented in the same component.

### D5 · major · A 400 or 500 from the API renders as "No tasks match these filters"

Unchanged. Contradicts **ERR-6**. Distinct from D1's mechanism, though D1's
reproduction 2 now lands on the same string.

The server's message is precise and is discarded entirely:

```
GET /api/tasks?limit=50&offset=0&status=not_a_status
→ 400 {"code":"validation_failed",
       "message":"unknown status value \"not_a_status\" at position 0",
       "field":"query","recovery":{"kind":"none"}}
```

UI: *"No tasks match these filters."*

A 500 is the same. `/list?view=01BOGUSBOGUSBOGUSBOGUSBOGU` returns 500 with
`detail: "unknown view …"` and renders the identical sentence. ERR-6
requires the server's reason verbatim and forbids flattening it to "Server
error" or "Something went wrong" — rendering it as a *successful empty
result* is further from the case than either string the case rejects.

**Reproduction:** `/list?status=not_a_status`, or
`/list?view=01BOGUSBOGUSBOGUSBOGUSBOGU`.

### D6 · minor · An unknown `sort` field silently reorders rather than erroring

Unchanged. `?dir=sideways` correctly 400s with *"Sort direction must be
ascending or descending."* `?sort=nonexistent_field` returns **200** and a
third ordering (`T1, T2, T3, T4, T5`), distinct from the default
(`PLAT7, T64, T65, …`) and from `sort=title`. A typo'd sort field should be
rejected the way a bad direction already is.

### D7 · minor · CSV export writes raw ULIDs where the UI shows names

Unchanged. `project`, `assignee`, `reporter`, `milestone` and `sprint` all
export as e.g. `01M0TH7SGNRQ47JVY1JCKNS7DA`. Someone opening the export in
Excel gets opaque ids in every reference column. The export is otherwise
correct — the filtered export returned exactly the 4 matching rows.

### D8 · minor · CSV formula injection is not neutralised

Unchanged. A task titled `=cmd|"/c calc"!A1` exports as
`"=cmd|""/c calc""!A1"` — correct CSV, but Excel and LibreOffice still treat
a leading `=`/`+`/`-`/`@` as a formula. Low exposure for a local tracker;
free to fix with a leading apostrophe or tab.

### D9 · minor · The task-detail stub prints an uninterpolated `$key`

Unchanged. `/tasks/T1` renders the literal `Route stub: /tasks/$key`. The
stub is expected (M2); printing the raw route pattern is a bug in the stub.
`/board` and `/timeline` interpolate correctly, so this is specific to the
parameterised route.

## Behaviour no case covers

Proposed cases only. **Nothing here has been written into
`docs/dev/ui-test-cases/`** — that directory is the specification and is
read-only to this gate.

- **PC-10 · No case requires a test to use a production-shaped QueryClient.**
  This is the deepest finding of the round and it is a testing-contract gap,
  not a UI one. Every `apps/web` test builds a throwaway client with
  `gcTime: 0` and `retry: false`; production uses one long-lived client with
  `staleTime: 30_000` and `retry: 1`. D1 exists *only* in the second
  configuration, which is why 69 green specs sit above four failing M1
  cases. Repo rule 2 ("is any test vacuous?") catches a test that passes
  with the behaviour deleted; it does not catch a test whose *harness* makes
  the bug unreachable. Worth a standing rule rather than a case.

- **PC-2 · No case distinguishes a failed *append* from a failed *replace*.**
  Carried over from round 2 and now better evidenced: LST-49 covers the
  append, LST-50 covers the replace, and one predicate serves both — which
  is how fixing one broke the other. A case should pin down the invariant
  behind both: *the rows on screen always correspond to the query the footer
  is counting, and the chips always describe a query that ran.*

- **PC-1 · Key sort is lexicographic, not natural.** `sort=key&dir=asc`
  gives `PLAT1, PLAT2, …, T1, T10, T11, …` — T2 lands after T19. The CLI
  does the same, so this is consistent core behaviour predating M1. A case
  should decide which it is.

- **PC-3 · Undo placement and lifetime are unspecified.** BLK-10 removed the
  typed confirm in favour of undo, but nothing constrains where undo appears
  or how long it lives. D4 exists in that silence. A case should require it
  within the viewport at the moment of the action.

- **PC-4 · No responsive contract exists for M1.** The 900px breakpoint is
  accepted (round 2). What is still missing is the contract underneath:
  *does the breakpoint apply on resize, or only on load?* D3 exists because
  the answer was never written down, and the fix picked "load only" without
  anything saying so.

- **PC-5 · Export field representation is unspecified.** Ids vs. display
  names (D7) and formula-injection neutralisation (D8) both need a stated
  intent.

- **PC-6 · Unknown query params are silently ignored.** `?bogusfilter=…`
  returns the full unfiltered set (200). Defensible, but undecided.

- **PC-8 · An empty tracker says "No tasks match these filters" with no
  filters applied.** Re-verified this round against a fresh `loctt init`
  with zero tasks on a separate port: the sentence names filters that do not
  exist, and is byte-identical to what a 400 shows and to what D1's
  reproduction 2 shows. Three different situations, one sentence. A
  first-run user's first screen should distinguish "you have no tasks yet"
  from "your filter matched nothing" from "the server is down".

- **PC-7 · `doctor`'s key-index check cannot detect a rekey.** It compares
  counts, so a key that changed identity leaves it reporting "in sync". No
  live trigger now that the move path is correct, but it remains the one
  diagnostic a user would run and it cannot see this class of corruption.

- **Positive findings worth locking in with cases.** Checked and correct
  this round: bulk-selection counts are honest across pages (50 → 50 with
  new rows unchecked → 52); the bulk bar is sticky and wraps cleanly at
  800px; the move toast names old **and** new keys for every task; the key
  index is byte-identical to a rebuild after a move; the export menu states
  its row count before committing; CSV escaping is RFC-4180-correct with
  Unicode intact and archived excluded; the DSL quoting chokepoint defeats
  injection (`x" or "1"="1` → 0 rows); `?limit=99999` is clamped to 200 and
  the URL rewritten to match; path traversal on
  `/api/tasks/../../../etc/passwd` returns the SPA shell, not a file;
  hostile titles are escaped in `innerHTML`; and **the write path's failure
  message remains exemplary** — a killed server during a bulk Set produced
  *"Nothing was updated — the operation could not run. (Failed to fetch)"*
  and `loctt show` confirmed disk untouched. That message is still the model
  the read path should copy, and it is still the only path that does it.

## What I could not test, and why

- **Mouse-wheel and drag.** `computer{action:"scroll"}` and
  `left_click_drag` time out consistently. For D2 this does not weaken the
  verdict: `overflow-x: auto` with `maxScrollLeft: 528` and a visible
  scrollbar is what makes native scrolling work, and both were measured.

- **Keyboard-only navigation.** Key events do not reach the document
  (`[` produced no state change and `stored` stayed `null`). The `[`-bypass
  noted under D3 is therefore recorded as a code observation, not a
  confirmed defect. This is an M4 journey and is not owed here.

- **Actual file download of the CSV.** The viewer sandboxes downloads. The
  real click was confirmed to issue `/api/tasks/export?status=…&assignee=…
  &format=csv` → 200, and the identical URL was fetched out-of-band and
  parsed with Python's `csv` module.

- **Why `useSidebarCollapse`'s resize listener does not re-render.** Observed
  and reproduced; not diagnosed. The finding rests on behaviour.

- **BLK-44** (one malformed `task.md` breaks every read) excluded as already
  recorded in `known-gaps.md`. Note again that **ERR-9 is an M1 blocker case
  covering exactly that behaviour**, so the known gap and the case remain in
  direct conflict — out of scope for this gate, but it has now survived two
  rounds unresolved.

- **Task detail, board, timeline, settings, init** are stubs by design and
  excluded per the brief. All render a stub inside the app shell rather than
  crashing. The one exception is D9.

## On the ✅ marks

Round 2's reading holds and is now sharper. **M1.4's own surface remains the
best-behaved part of this build** — bulk bar, pagination, export, move,
archive undo all did what they claim, with honest counts and correct
persistence, and the move fix stood up to a rekey plus an index diff.

Every blocker still lives in M1.2's error surface. Those tickets are marked
✅ at 0/75, 10/67 and 3/44 cases covered, and the four cases failing here —
ERR-1, ERR-2, ERR-6, LST-50 — have **no test claiming them at all**. The ✅
marks record "the bullets were built"; three gate rounds have now confirmed
that is not the same as "the cases pass".

**The one thing I would change about how this round was fixed.** The commit
message states a correction to the gate ("I could not reproduce the full
claim… smaller than reported") and then fixes the smaller thing. The larger
thing reproduced on my first attempt from the written steps. A correction to
a gate finding is itself a claim, and this repo's own rule — *verify claims
against source before repeating them; an earlier finding is a claim, not a
fact* — cuts both ways. The cheapest guard is to paste the gate's literal
steps into the terminal before writing the paragraph that supersedes them.
